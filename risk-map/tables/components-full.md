| componentAgentConsentSurface                      | Agent Consent Elicitation Surface                       | The **agent consent elicitation surface** is the control point at which an autonomous agent pauses its own workflow to elicit explicit human confirmation before performing a consequential or irreversible tool action. It renders an elicitation request describing the pending action and returns the user's allow-or-deny decision to gate execution, generalizing protocol-specific confirmation primitives such as the server-side elicitation requests defined in [Model Context Protocol Specification: Elicitation](https://modelcontextprotocol.io/specification/2025-06-18/client/elicitation).<br><br> This surface owns the agent-driven elicitation prompt and the decision it returns. Because the agent itself initiates the request mid-loop and the prompt content can be populated by agent- or server-returned data, the surface is also an untrusted input channel: confirmation content must be sanitized before display and each returned approval must be integrity-bound to the exact action it described, so a compromised upstream cannot spoof, replay, or re-target the consent.<br><br> What separates this surface from Application Consent Surface is where the decision is taken. An application approval step interrupts a user already engaged with the application, holding the context the decision needs; an elicitation is raised mid-loop, on the agent's initiative, to a user who may not be present and did not ask the question. Request volume follows from that locus rather than defining it: a naively designed agent elicits confirmation on a high proportion of its tool calls, so habituation pressure on the human approver accumulates here. Effective designs reserve elicitation for genuinely consequential or irreversible actions and bind each approval to one specific action rather than a standing class.<br> | componentAgentNetworkPolicyEnforcementPoint       | Agent Network Policy Enforcement Point                  | The agent network policy enforcement point is the client-side data-plane control through which the agent's outbound traffic transits — its tool-call traffic to external tool servers and services, typically over a tooling protocol such as the Model Context Protocol ([Model Context Protocol specification](https://modelcontextprotocol.io/specification)), and its model-serving traffic to Model Serving Infrastructure & Policy Enforcement Point, and traffic handed off to or received from the hosting application via Application Network Policy Enforcement Point as a peer — the two enforcement points connect directly to each other rather than either one reaching past its counterpart into the other tier's output/input gates. These classes of traffic share this one enforcement point because they cross the same operator's egress boundary under the same reviewed policy; splitting them across separate agent-side PEPs would leave two narrower gates covering one boundary. Orchestration is not a further class of traffic here: it has no PEP of its own and no edge to this one, reaching Model Serving Infrastructure & Policy Enforcement Point directly as the served model's own machinery rather than as agent-operator-controlled egress. It is a Policy Enforcement Point in the [NIST SP 800-207 — Zero Trust Architecture](https://doi.org/10.6028/NIST.SP.800-207) sense — the runtime element that enables, monitors, and terminates connections — applied at the network layer on the agent operator's side: it admits or blocks each outbound connection against the operator's reviewed egress policy and enforces transport protections such as allowed destinations, TLS/mTLS, rate limiting, and audit on the traffic it carries ([NIST SP 800-162 — Guide to Attribute Based Access Control (ABAC) Definition and Considerations](https://csrc.nist.gov/pubs/sp/800/162/upd2/final)).<br><br> Its security value is enforcement of a reviewed policy, not centralization. Realized as a per-agent sidecar in a service-mesh data plane rather than a single shared gateway, each agent container gets its own enforcement instance — the same control without a single chokepoint to compromise or take offline, with [MITRE ATT&CK M1037: Filter Network Traffic](https://attack.mitre.org/mitigations/M1037/)-style egress filtering applied close to the workload. It remains a high-value trust boundary: a compromised or misconfigured instance can blind the audit trail, leak the credentials it terminates, or relax the policy it enforces.<br><br> It is distinct from Authorization Policy Enforcement Point, which enforces an allow-or-deny authorization decision on whether an action is permitted: this component governs how and to where the traffic may flow, not whether the action is allowed. As a network-layer control it nests outside the content-layer input and output handling — connection enforcement wraps prompt and context enforcement. It is the client-side half of a pair: the resource-side Tool Network Policy Enforcement Point enforces the remote tool provider's ingress policy at the other end of the same connection, carried between them by Agent Tool Transport Channel, which owns the wire; the pairing between the two enforcement points is a logical relationship rather than a path of its own. It consults Identity Provider and Authorization Policy Decision Point as control-plane peers for the identity and policy context its own egress decisions rest on, the same relationship the resource-side PEP already has with them, and Tool Registry and Discovery as a third such peer, for the tool-call class of traffic only: an allowed-destination list is an egress question, so it is this side of the connection that admits an outbound *tool* call only to an endpoint the registry enumerates. Its other two traffic classes are not gated on that registry — model-serving destinations resolve through Model Registry and Marketplace at Model Serving Infrastructure & Policy Enforcement Point, and the application handoff is a peer relationship. Where the call crosses into another identity domain it receives the delegated credential from Authorization Federation Proxy and presents it on the outbound connection, which is why a compromised instance can leak the credentials it terminates: it puts borrowed authority on a wire, which Authorization Federation Proxy mints and binds but does not itself transmit.<br> | componentAgentToolTransport                       | Agent Tool Transport Channel                            | The communications channel that carries request and response messages between the agent's own network enforcement point and the tool provider's network enforcement point. It frames, delivers, and returns structured calls — typically JSON-RPC 2.0 messages ([JSON-RPC 2.0 Specification](https://www.jsonrpc.org/specification)) — over either a local inter-process stream or a networked session, abstracting the same agent-to-tool exchange across local and distributed deployments, as specified for remote-tooling protocols such as the Model Context Protocol ([Model Context Protocol specification — architecture and JSON-RPC messaging](https://modelcontextprotocol.io/specification)).<br><br> This channel owns the transport between Agent Network Policy Enforcement Point and Tool Network Policy Enforcement Point: the underlying stream or socket and the session that carries messages in flight across the network boundary the two PEPs sit at opposite ends of. It owns the wire the PEP pairing enforces over: the client-PEP / channel / resource-PEP shape this trust-boundary crossing uses, where other PEP pairings peer directly with no channel between them. Mutual authentication of the calling and serving ends is exercised here, though issuing and deciding that authentication is the job of dedicated components elsewhere in the graph (Identity Provider, Agent Network Policy Enforcement Point). It is distinct from the tool itself, which performs the invoked action; the channel only conveys the call to and from that endpoint.<br><br> The key distinction is that this is a connecting locus rather than an action endpoint. Transport-level assurances are established or lost here, independent of whether the tool endpoint is itself sound.<br><br> This channel also multiplexes calls across one or more remote servers from a single agent. Identity verification is not limited to session establishment: each incoming response is checked against the remote server's verified identity, so a server impersonated or substituted after the session begins is caught before its response is trusted. Scoped, short-lived credentials issued per session are preferred over forwarding long-lived tokens, bounding what a captured credential can reach and for how long.<br> This channel is also a trust boundary: tool servers and network intermediaries reaching it are often untrusted, so malformed or hostile frames, deserialization of attacker-controlled payloads, and session-lifecycle confusion from replayed or out-of-order initialization are the primary threats it must withstand, independent of whether the invoked tool logic is itself sound. The session it carries follows a defined lifecycle of initialization, capability negotiation, and teardown, governing how a connection is established and retired rather than just how messages are carried once in flight. Realizations extend beyond [JSON-RPC 2.0 Specification](https://www.jsonrpc.org/specification) framing under the Model Context Protocol to other agent-to-tool wire protocols such as gRPC and REST-over-HTTP, with encoding and deployment form varying while the channel's role stays the same. Payload-level validation of the calls themselves is out of scope for this channel and belongs to Tool Input Handling and Tool Output Handling on the far side of the resource-side PEP. | componentAuditRecordRepository                    | Audit Record Repository                                 | The durable, tamper-evident storage substrate that other components write their logs and audit records to. Tools are the external APIs and services that agents invoke (the tool functionality); the registry is the catalog/metadata layer that informs which tool is selected and how the agent should invoke it. The threat models are distinct: attacks on tools target functionality (Insecure Integrated Component), while attacks on a registry target the metadata that directs tool selection (Tool Source Provenance, Tool Registry Tampering). A compromised registry can redirect an agent to the wrong tool — or to a corrupted invocation method on the right tool — even when the tools themselves remain secure.<br><br> Registries are decoupled from tools: the same tool may be referenced by multiple registries from different sector-focused authorities (compliance-flavored, performance-flavored, licensing-flavored), and registries are not required in all deployments — internal-only or air-gapped agent systems may operate without any public registry layer. Controls targeting registry integrity apply only where a registry is part of the deployment.<br><br> The registry's scope also extends to the *publication and registration* step through which extensible artifacts — plugins, connectors, skill packages, and MCP server bundles — are made available and added to the catalog before they are installed into the agentic system. This is the point at which a new extension's metadata (its capability declarations, publisher identity, and invocation method) first enters the registry, expanding the set of External Tools and Services an agent can invoke; it precedes and feeds the selection and invocation metadata this component already governs.<br> The registry is also the authored inventory that governance processes act over: the enumerated set of tools, services, and serving endpoints an agentic system is permitted to reach, each carrying a trust-state marker that lets stale or unauthorized entries be flagged before a call is routed to them.
