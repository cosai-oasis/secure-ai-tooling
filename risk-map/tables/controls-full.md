| controlTrustedPolicyEnforcementPoint         | Trusted Policy Enforcement Point                  | Ensure that the security-critical authorization decision and its enforcement are carried out by trusted, deterministic components outside the model's influence. This control governs where the decision and its enforcement are placed.<br>                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | Treat the model's output as a request to be checked, not an authority to be trusted: a separate decision component determines whether a requested operation is permitted, and a separate enforcement component rejects or constrains anything outside policy before any side effect occurs. Record, from those trusted components rather than from the model, each permit, deny, or constrain outcome with the principal, the requested operation and its object, the policy relied on, and the time. See [CoSAI — MCP Security Considerations](https://github.com/cosai-oasis/ws1-supply-chain).<br><br> The role is locus-defined and protocol-independent: it applies wherever a model's output gates a privileged operation, whether the call rides over MCP, A2A, an in-process tool interface, or any other remote-tooling channel.<br><br> The model is influenceable by untrusted content reaching its context (for example via Prompt Injection), so a system that relies on the model to authorize an action or hold a guardrail can be steered into actions the requester was never entitled to take. In the classical access-control model ([NIST SP 800-162: Guide to Attribute Based Access Control (ABAC) Definition and Considerations](https://csrc.nist.gov/pubs/sp/800/162/upd2/final)) the model is neither the policy decision point nor the policy enforcement point: both live in components the attacker cannot reach through the model's context window. The enforcement point this control requires is a reference monitor: tamperproof, always invoked, and small enough to be subject to analysis and testing (AC-25 in [NIST Special Publication 800-53 Revision 5: Security and Privacy Controls for Information Systems and Organizations](https://doi.org/10.6028/NIST.SP.800-53r5)).<br><br> This control is distinct from Externalized Authorization Decisioning and Resource Authorization Enforcement, which assume trustworthy decision and enforcement points and specify how the decision is externalized and where it is enforced; this control establishes that the model is neither. It is distinct from Agent Permissions (which bounds the action scope an agent is granted) and Input Validation and Sanitization (which filters adversarial input to the model rather than relocating authorization out of it). Showing that this control was enforced depends on the records described above being committed and retained under Audit Trail Completeness.<br>
