# Framework Mappings Audit

Audit framework mappings for correctness, style compliance, and term validity.

## Scope

Three modes, chosen by what the caller provides — each is a first-class mode, not a side effect of another:

- **Single entity**: a specific entity id already in the corpus (e.g., `riskModelEvasion`, `controlInputValidationAndSanitization`, `personaEndUser`). Audit that entity's existing mappings, or a new value being proposed for addition to that entity. Both are single-entity scope: the entity already exists, so this is distinct from candidate mode below, which is for an entity that does not exist yet.
- **Whole corpus** (the default): every entity across `risks.yaml`, `controls.yaml`, `personas.yaml`.
- **Candidate value(s)** for an entity not yet in the corpus (pre-PR authoring): audit the given value(s) directly. No corpus id lookup applies — the entity doesn't exist yet, so there is nothing to look up by id. The caller must also state the entity type the candidate targets (risk, control, or persona), since parts of the checklist (e.g., MITRE ATLAS technique-vs-mitigation) depend on it. See [Candidate mode checklist](#candidate-mode-checklist-pre-pr-entity-not-yet-in-corpus).

## Reference documents

Read these before auditing:

1. **Style guide** (authoritative): `risk-map/docs/contributing/framework-mappings-style-guide.md`

## Audit checklist (for whole-corpus and single-entity scope)

For each entity with mappings, verify ALL of the following. Report pass/fail per item. Candidate mode (an entity not yet in the corpus) does not have "mappings" on an entity to iterate over — it uses its own [Candidate mode checklist](#candidate-mode-checklist-pre-pr-entity-not-yet-in-corpus) below instead.

### Format and version compliance

Mapping values are **version-pinned** (ADR-027): every value carries its framework's version token, except STRIDE, which is intentionally unversioned. Verify each value against the **canonical pinned pattern for its framework in the authoritative style guide** (`risk-map/docs/contributing/framework-mappings-style-guide.md`, "Identifier Enforcement" table) — read the patterns from the guide every time; do not restate them from memory or inline here. The guide is the single source for pattern and version-token conventions across every supported framework, including any framework registered after this skill was written — new frameworks are a recurring, actively-requested change (see open issues against `frameworks.yaml`), so nothing about the pinned-pattern set may live in two places.

Flag any value whose form or version token does not match the guide's current pinned pattern. A **new** value (a candidate, or a value proposed for addition to an existing entity) pinned at a still-valid prior edition (listed in the framework's `priorVersions` in `frameworks.yaml`) passes, with the same **advisory** as candidate-mode step 1: compose new values at the framework's registered `version`. Values already in the corpus at a prior edition are retained pins; report them as information only.

*(Division of labor: `mapping-selection` makes the affirmative, broader authoring judgment of WHICH mappings to propose in the first place — browsing the corpus, picking the components/risks a control or risk should connect to, choosing the correct NIST AI RMF function — before a candidate value exists. This skill, in any of its three scope modes including candidate mode, then audits the chosen or proposed value(s): well-formed, current, structurally sound, AND not over-selective or tangential. Selectivity compliance (the soft cap, direct relevance — see [Selectivity compliance](#selectivity-compliance) and candidate-mode step 3) is explicitly part of THIS skill's checklist in every mode, not `mapping-selection`'s exclusive territory — it runs whether the entity is new (candidate) or already exists.)*

### Structural compliance

- [ ] **No parent + sub-technique collisions**: If `AML.T0010.002` is used, `AML.T0010` must NOT appear on the same entity
- [ ] **No technique/mitigation crossover**: Risks use only `AML.T####`; controls use only `AML.M####`
- [ ] **applicableTo respected**: Each framework is only used on entity types listed in its `applicableTo` (per style guide table)

### Selectivity compliance

- [ ] **Soft limit (4 per framework)**: Flag any entity with more than 4 mappings in a single framework. Not a hard error, but requires justification.
- [ ] **Direct relevance**: Each mapping should be defensible with a one-sentence rationale. Flag mappings where the connection is "related" rather than "directly relevant."

**Non-recognition is not a relevance finding.** Judging a value "not directly relevant" (or "cannot be judged relevant") requires actually knowing what the value represents — from established domain knowledge, or from having just live-verified it (see [Term and identifier verification](#term-and-identifier-verification) / candidate-mode step 4). Not recognizing an identifier — "I don't know what this is" — is not itself a relevance judgment; it is an admission that the information needed to judge relevance doesn't exist yet, and it must be resolved via live-verify before a relevance/selectivity disposition is possible for that value. This cuts both ways: an agent applying "I don't recognize it, therefore not relevant" would just as wrongly reject a real-but-obscure value it simply doesn't happen to know. The exception is a framework whose identifier structure itself conveys real semantic information the agent can reason about without first identifying the specific value — e.g., NIST AI RMF's function prefix (`GOVERN-`/`MAP-`/`MEASURE-`/`MANAGE-`) names the function even when the specific subcategory is unfamiliar, so a function-level relevance objection (e.g., rejecting a MANAGE subcategory for a preventive design control) can legitimately fire before live-verify, because the prefix itself is real, known information — not a guess. MITRE ATLAS mitigation numbers (`AML.M####`) are opaque: the number alone conveys nothing about content. For an ATLAS candidate the agent doesn't already recognize, no pre-live-verify relevance judgment is possible — live-verify is the only way to learn what it is, and if it turns out not to exist, that absence (not a guessed-at relevance rationale) is the disposition.

### Term and identifier verification

Two distinct checks — do not conflate them. The first is structural and runs at whatever scope the audit is already covering; the second is a live, per-entity or per-candidate-value lookup that is never an automatic side effect of the first.

- [ ] **Verify identifiers are well-formed against the style guide's patterns.** For MITRE ATLAS, technique/mitigation IDs match the pinned regex. For OWASP, the category title matches the guide. For ISO 22989, role names match the controlled vocabulary. This is a structural check — no live lookup — and applies at whatever scope the audit already covers, whole-corpus included, the same as the structural-compliance and selectivity checks above.
- [ ] **Live-verify identifier currency (search the web)** when a specific identifier's currency is actually in question: proposing a **candidate** mapping value (per Scope; see [Candidate mode checklist](#candidate-mode-checklist-pre-pr-entity-not-yet-in-corpus)), or auditing a single **targeted** entity (per Scope) — whether confirming an identifier already on that entity, or a new value being proposed for addition to it. Verify against the **edition the value's own version token names** — not the `version` registered for that framework in `frameworks.yaml`, and not simply whatever the framework's live/current site serves. For MITRE ATLAS the token resolves through the vendored manifest (`scripts/framework_catalogues/mitre-atlas/manifest.yaml`, per ADR-038 D3b): the release whose name equals the token, otherwise the unique release carrying that format-version. So `@2026.09` (the current edition) resolves to release `2026.09`, and `@5.0.1` (a still-valid prior edition) resolves to release `2025.10`. A live catalog can run ahead of the value's edition, and an identifier that is real but was only added in a later edition than the one its token names is not yet valid at that edition and must be flagged, not confirmed. This is a heavier, per-entity or per-candidate-value check. **It is not run automatically across every entry as a side effect of a whole-corpus audit** — a whole-corpus audit's job is the structural/selectivity/overlap sweep above, not a live web-search of every existing mapping in the file. If comprehensive liveness verification of the full corpus is genuinely wanted, invoke it as its own explicit, separately-requested pass — never as an implicit consequence of the routine audit. **Exception:** a framework skips this step entirely only if its full identifier space is a closed, finite set of literal values — no numeric or wildcard component (a regex digit-class placeholder like `\d`, not merely a digit character appearing within an otherwise-fixed literal string) that could ever admit a new value without a schema change — AND is unversioned (no per-edition variant). Both halves of that test matter — closed-and-literal AND unversioned — not one alone, and neither turns on which JSON-schema keyword encodes the set: five of the six frameworks' pinned forms are a regex `pattern` — including STRIDE — and the sixth, ISO 22989, is a JSON-schema `enum`; so "closed" here means a fixed, finite set of literal values, not a choice of `enum` over `pattern`. This closed-literal-and-unversioned test is a mechanically checkable proxy for the real underlying question — is there an external process that can add, retire, or rename a member independent of this repo's own schema or version? — and it happens to correctly classify all six frameworks currently registered in `frameworks.yaml`. A future framework should ultimately be checked against the real question, not just the mechanical proxy: a framework could in principle present as a closed literal alternation and unversioned yet still be governed by an external body that revises membership without ever forcing a version bump here, in which case the proxy would wrongly exempt it and the real question should govern instead. For frameworks meeting both halves of the proxy today, the structural/membership check above is their complete verification. MITRE ATLAS, NIST AI RMF, OWASP Top 10 for LLM, and EU AI Act never qualify for this exemption, regardless of how infrequently a given edition changes, because each one's pinned pattern contains a numeric component (`AML\.(T|M)\d{4}`, subcategory numbers, `LLM\d{2}`, article numbers) that admits new values indefinitely without any schema change. ISO 22989 also does not qualify: its schema definition is a fixed literal set (an `enum` nested in a `oneOf`), but it is *versioned* (`@2022`), and `risk-map/schemas/frameworks.schema.json`'s `iso-22989` definition is deliberately structured so each future ISO 22989 edition appends a new `oneOf` member carrying that edition's own enum — i.e., ISO periodically revises 22989 through a real external process that can add, retire, or rename role descriptors, exactly what live-verify exists to catch. STRIDE is the only framework that is both a closed, finite literal alternation and unversioned, which is why it alone is the current instance of this exception (see [Candidate mode checklist](#candidate-mode-checklist-pre-pr-entity-not-yet-in-corpus) for why).

### Candidate mode checklist (pre-PR, entity not yet in corpus)

Candidate mode audits a value (or set of values) intended for an entity that does not yet exist in the corpus — there is no entity id to look up. The caller must state the entity type the candidate targets (risk, control, or persona) before this checklist can run, since step 2 depends on it (e.g., MITRE ATLAS technique-vs-mitigation). **If the entity type is not stated, halt and ask the caller for it — never infer, default, or silently proceed.** For each candidate value, run, in order:

1. **Format/version compliance** — the same check as [Format and version compliance](#format-and-version-compliance) above: match the value against the canonical pinned pattern for its framework in the style guide. A candidate pinned at a still-valid prior edition (one listed in the framework's `priorVersions` in `frameworks.yaml`, e.g. MITRE ATLAS `@5.0.1`) **passes**, with an **advisory**: compose new values at the current edition, the framework's registered `version` (MITRE ATLAS `@2026.09` today).
2. **Full structural compliance** — the same checklist as [Structural compliance](#structural-compliance) above, evaluated against the stated entity type and against the full set of values proposed together (not each value in isolation): parent/sub-technique collisions, technique/mitigation crossover, `applicableTo`. A well-formed value can still fail here — do not stop at step 1.
3. **Selectivity compliance** — the same checklist as [Selectivity compliance](#selectivity-compliance) above, evaluated against the full set of candidate values proposed together (not each value in isolation): the soft limit of 4 mappings per framework, and direct relevance. A set of candidate values can each pass structural compliance individually and still be over-selective as a set — do not stop at step 2. **The "full set" must be the caller's complete intended set, not whatever has been mentioned so far.** If the caller's prompt signals that more candidate values may follow for this entity/framework combination (e.g., says "I'll have more later," "I might add a couple more," or similar), ask the caller to confirm the complete set of candidate values before finalizing a selectivity verdict, rather than evaluating the partial set as final — a partial view risks seeing a "full set" of size one or two and never catching a cross-value overshoot of the soft cap once the remaining values arrive. **"No defensible relevance rationale" is not a legitimate reason to stop at this step unless the rejection is grounded in the identifier's own structure** (e.g., a NIST function-prefix mismatch) **rather than mere non-recognition of an opaque identifier** (e.g., an unfamiliar MITRE ATLAS mitigation number) — see [Non-recognition is not a relevance finding](#selectivity-compliance) above. For an opaque, unrecognized candidate, the relevance sub-check cannot be resolved at step 3 without first knowing what the value is, so the checklist effectively continues to step 4 (live-verify) for such values.
4. **Live-verify identifier currency against the edition the value's own token names (search the web, but confirm against that edition, resolved as in [Term and identifier verification](#term-and-identifier-verification) — not the version registered in `frameworks.yaml`, and not just the live/current site)** — a candidate value's currency is always in question, so this step always applies, **except for frameworks with no external evolving registry to check currency against**: a framework whose full identifier space is a closed, finite set of literal values — no numeric or wildcard component that could ever admit a new value without a schema change — AND is unversioned (no per-edition variant). Both halves of that test matter — closed-and-literal AND unversioned — not one alone, and neither turns on which JSON-schema keyword encodes the set. This two-part test is the mechanically checkable proxy for "no external evolving registry" (see [Term and identifier verification](#term-and-identifier-verification) above for why it is a proxy and not the definition itself) — it correctly classifies STRIDE today. The override runs one direction only: for any newly registered framework, if the real underlying question would require live-verify where the proxy's two-part test says exempt, the real question governs and live-verify still applies — the proxy is never grounds to skip live-verify for a framework the real question would flag. STRIDE is the current instance of this exception: see the style guide's Identifier Enforcement table for STRIDE's canonical pinned pattern (a fixed alternation of six literal strings and nothing else, unversioned, with no external registry that issues new members over time). A live web search against a closed set like this is a no-op at best; at worst it surfaces out-of-set variants from adjacent but distinct models (e.g., STRIDE-LM's added "Lateral Movement" category) that this repo's schema rejects, and mistaking a web hit for a valid addition would introduce a value that fails `check-jsonschema`. MITRE ATLAS, NIST AI RMF, OWASP Top 10 for LLM, and EU AI Act never qualify for this exemption, regardless of how infrequently a given edition changes, because each one's pinned pattern contains a numeric component that admits new values indefinitely without any schema change — for example, NIST AI RMF's pattern permits any subcategory number, so a fabricated value like `MEASURE-2.99@1.0` would pass the schema and still requires live-verify. ISO 22989 also does not qualify for this exemption: its schema definition is a fixed literal set (an `enum` nested in a `oneOf`), but unlike STRIDE it is *versioned* (`@2022`), and `risk-map/schemas/frameworks.schema.json`'s `iso-22989` definition documents that each future ISO 22989 edition appends a new `oneOf` member for that edition's own enum — ISO periodically revises 22989, so its role descriptors have a real external revision process (additions, retirements, renamings) that live-verify exists to catch, distinct from the open-ended-numeric-pattern reason MITRE ATLAS/NIST/OWASP/EU AI Act are excluded. For STRIDE-class frameworks, the closed-set-membership check inside step 1 (format/version compliance) is the complete verification — report it as such rather than silently skipping the step (see [Output format](#output-format)).

This mechanism generalizes: any framework registered in `frameworks.yaml` with no external evolving registry behind its identifiers — mechanically, one whose pinned pattern is a fixed, finite alternation of literal values with no numeric or wildcard component, AND which carries no version/edition token — is exempt from step 4 on the same reasoning. As above, this is a proxy for the real question of whether an external process can add, retire, or rename a member independent of this repo's schema/version; a future framework should be checked against that question, not the mechanical test alone, and the check runs one direction only — the real question can pull a framework into requiring live-verify even when the mechanical test would exempt it, never the reverse. A numeric or wildcard component is sufficient on its own to disqualify a framework, because its identifier space stays open-ended regardless of which JSON-schema keyword expresses it — this is why MITRE ATLAS, NIST AI RMF, OWASP Top 10 for LLM, and EU AI Act are disqualified, independent of the fact that all four also carry version tokens (`@2026.09`, `@1.0`, `:2025`, and `@2024` respectively; MITRE ATLAS also admits its prior edition `@5.0.1`). ISO 22989 has no such numeric component but is disqualified on the version-token ground alone: its closed literal set is versioned via a per-edition `oneOf` member, meaning a real external revision process exists. STRIDE is the only framework meeting both conditions — no numeric/wildcard component and no version token — today.

## Coverage analysis (for whole-corpus scope only)

- Count entities with vs. without mappings per entity type
- Identify unmapped entities where obvious framework matches exist
- Note underutilized frameworks (e.g., NIST AI RMF, OWASP LLM08)
- Note STRIDE categories never used

## Output format

For targeted audits (single entity), provide:

1. Current mappings listed per framework
2. Pass/fail on each checklist item
3. Any recommended additions or removals with rationale

For candidate mode (values for an entity not yet in the corpus), provide, per candidate value:

1. Pass/fail on format/version compliance, plus the current-edition advisory when step 1 raises it
2. Pass/fail on each structural compliance item (parent/sub-technique collision, technique/mitigation crossover, `applicableTo`)
3. Pass/fail on selectivity, evaluated against the full candidate set (soft cap of 4 mappings per framework, direct relevance)
4. The live-verify result (found current / not found / doesn't exist / real in the current live catalog but added only in an edition later than the one the value's token names — report this case as "not yet valid at the pinned edition" and flag it rather than confirming it as current), or, for a framework with no external registry (STRIDE-class), the explicit statement "live-verify not applicable (closed literal set, unversioned, no registry)" rather than omitting the item
5. An overall accept/reject recommendation for the value, with rationale for any failure. If the complete candidate set could not be confirmed (per step 3's drip-feed clause), report the recommendation as provisional/pending rather than a final accept/reject, and state what is needed to finalize it (confirmation of the complete candidate set)
